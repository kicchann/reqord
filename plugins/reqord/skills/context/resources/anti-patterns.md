# アンチパターン集・チェックリスト

## 要件定義のアンチパターン

### 巨大要件（God Requirement）

- **症状**: 1要件に複数機能が混在。工数40時間超。成功基準10個以上
- **問題**: レビュー滞留、Issue分解困難、部分完了の判定不能
- **対処**: 1要件=1機能/1振る舞い。40時間超は分割。「1文で説明できるか？」で判定

### 曖昧要件

- **症状**: 「適切に処理する」「高速に応答する」「使いやすいUIにする」
- **問題**: 解釈のばらつき、テスト不可能、ツール自動処理の精度低下
- **対処**: 数値・条件を明示。SMARTバリデーション実行

| カテゴリ | 避けるべき表現                                         |
| -------- | ------------------------------------------------------ |
| 程度     | 適切に、なるべく、できるだけ、可能な限り、必要に応じて |
| 品質     | 高速、効率的、柔軟、簡単、使いやすい、わかりやすい     |
| 相対     | 多い、少ない、大きい、小さい、良い、悪い               |
| 包括     | 等、など、その他、ある程度、十分に                     |

### 実装詳細の混入

- **症状**: 要件に「Reactで実装」「PostgreSQLに保存」「REST APIで提供」
- **問題**: What/Howの境界曖昧化、技術変更時に要件まで変更必要、代替案の検討阻害
- **対処**: 要件には「何をしたいか」だけ。技術選択はSpecificationで行う
  - 悪い例: 「JWTでセッション管理」
  - 良い例: 「ログイン状態を保持できること」

### 依存関係の放置

- **症状**: blockedByだけ設定してblocks未設定。relatedTo未使用
- **問題**: 片方向リンクでは影響分析が不完全
- **対処**: 双方向リンク必須。定期的に依存関係グラフを確認

### 循環依存

- **症状**: A→B→C→A のようなループ
- **問題**: 実装開始点が決められない、影響分析が無限ループ
- **対処**: 循環の原因分析、要件分割、共通部分の切り出し

### 影響分析なしのdeprecation

- **症状**: 紐づくspecの状態や依存先reqを確認せずにreqをdeprecatedに変更
- **問題**: 実装中のspecが宙に浮く、依存先reqのblockedByが破壊される、トレーサビリティ断絶
- **対処**: deprecated前に `/reqord:verify trace <req-id>` で影響範囲を確認。紐づくspecの対応（別reqへの付け替え or 破棄）を決定してからステータス変更

## ワークフローのアンチパターン

### 承認スキップ

- **症状**: draftのまま実装開始。承認フローを経由せずimplementedにする
- **問題**: 手戻りリスク増大、トレーサビリティ損失、チーム合意なき実装
- **対処**: 必ず draft → approved のフローを踏む。急ぎでも簡易レビュー+承認を実施

### 過度な構造化

- **症状**: バグ報告や改善要望を最初からフル構造化しようとする
- **問題**: 不十分な情報での構造化は無駄。フィードバックの初動遅延
- **対処**: まずGitHub Issueでシンプルに報告。調査後に構造化（3段階進化モデル）

### コンテキスト不足でのAI利用

- **症状**: ProjectContextが空の状態でAIのenhance/refineを実行
- **問題**: 汎用的で的外れな出力、ドメイン用語の誤用、技術スタック不適合
- **対処**: AI利用前に最低限 product.yaml + technical.yaml を充実させる

### バージョン管理の軽視

- **症状**: approved済み要件をステータス変更せずに直接編集
- **問題**: 承認済み要件が無断変更、実装との乖離、過去の承認が無効化
- **対処**: approved要件の変更は新バージョンとして扱い、PRで再承認

## AI利用のアンチパターン

### AI出力の無批判な受け入れ

- **症状**: enhance/refineの結果をレビューせずに承認
- **問題**: ドメイン知識不足、ビジネスルール誤解、セキュリティ要件見落とし
- **対処**: AI出力は「下書き」。ドメイン用語の正確性、ビジネスルール整合性、セキュリティ考慮を必ず確認

### AIに全てを任せる

- **症状**: 要件定義からIssue生成まで人間の判断なしにAI一括実行
- **問題**: 優先度・スコープはビジネス判断。ドメイン知識は人間が持つ。責任所在の不明確化
- **対処**: AIは支援ツール。判断ポイント（優先度、スコープ、承認）は人間が担う

### 構造化せずにAI投入

- **症状**: free-formで漠然とした文章を書き、AIにenhanceさせる
- **問題**: Garbage In, Garbage Out。AIが意図を推測し本来の意図と乖離
- **対処**: まず人間がUser Story/EARSテンプレートに沿って骨格を書いてからAIに詳細化を依頼

## データ管理のアンチパターン

### .reqord/ をgitignore

- **問題**: トレーサビリティ消滅、チームメンバーがアクセス不能、PRベース承認フロー不能
- **対処**: `.reqord/` はGit管理下に置く。個人設定のみ `.gitignore` に追加

### YAML手動編集でバリデーション無視

- **問題**: Zodバリデーションスキップ、必須フィールド欠落、ステータス遷移ルール違反
- **対処**: CLIコマンド経由で操作。直接編集時は `reqord validate` を実行

## チェックリスト

### 要件作成時

- [ ] 1要件 = 1機能/1振る舞いになっているか
- [ ] 曖昧な表現（適切に、高速に等）が含まれていないか
- [ ] 成功基準が3〜7個あり、検証可能か
- [ ] 実装詳細（技術選択）が混入していないか
- [ ] 依存関係が双方向に設定されているか
- [ ] SMARTバリデーションを実行したか
- [ ] 工数見積もり（complexity + hours）が設定されているか

### ワークフロー確認

- [ ] 承認フロー（draft → approved）を経由しているか
- [ ] AI出力を人間がレビューしたか
- [ ] ProjectContextが充実しているか（最低限 product.yaml + technical.yaml）
- [ ] `.reqord/` がGit管理下にあるか
