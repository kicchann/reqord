# AI支援フェーズ・Human-in-the-loop境界

## 核心的な設計

reqord CLIは要件/仕様/issue/feedbackの**データ管理基盤**であり、AI機能を内包しない。AIはCLIの外側（Claude Codeプラグイン、Cursor、Codex等）からreqordの構造化データを読み書きすることで、持続的な開発を実現する。

### CLIとAIの責務分離

| 責務   | reqord CLI                                                        | AIツール                                                     |
| ------ | ----------------------------------------------------------------- | ------------------------------------------------------------ |
| 役割   | データのCRUD、バリデーション（SMART）、ステータス遷移、GitHub連携 | 構造化データを入力として、詳細化・設計・実装・レビューを支援 |
| AI依存 | なし（AI無しで完全動作）                                          | reqordデータが入力品質を決める                               |

## なぜReqordとAIの組み合わせが有効か

構造化・承認フロー・トレーサビリティは人間のチームだけでも価値がある。AI時代には追加で以下の価値が生まれる:

1. **構造化データ → AIへの明確な入力**: 曖昧な自然言語ではなく、型付きのYAML + Markdownを渡せる
2. **ProjectContext → セッション間の一貫性**: AIセッションが切れても文脈を再現できる
3. **可視化 → 人間の状況把握**: AIがコードを高速生成する環境で「何を作っているか」を見失わない

## AIが活用する4つのフェーズ

これらはreqord CLIではなくAIツール側の責務。

### 1. 要件詳細化（Enhancement）

タイトル+概要 → EARS/User Story + 成功基準 + 複雑度見積もり

- EARS形式 / User Story形式への変換
- 成功基準（Success Criteria）の定義
- 複雑度の見積もり、依存関係の推定
- SMARTバリデーションによる品質スコアの改善

### 2. Gap Analysis

要件 + 既存コード → カバレッジ評価 + 不足機能 + コンフリクト検出

- 既存実装のカバレッジ評価（full / partial / no coverage）
- 不足機能の特定
- コンフリクト検出（API変更、データモデル不整合等）

### 3. 仕様設計（Specification Design）

要件 + ProjectContext → design.md（アーキテクチャ、コンポーネント設計、技術的決定）

- アーキテクチャ図（Mermaid形式）
- コンポーネント設計とインターフェース定義
- 技術的決定の文書化（Rationale、Alternatives、Tradeoffs）

### 4. タスク分解（Task Decomposition）

仕様 → GitHub Issues（並列グループ、クリティカルパス）

- レイヤー別 / 機能別 / 要件別の分解戦略
- 並列実行分析（Parallel Group: P0, P1, P2）
- クリティカルパスの特定
- GitHub Issueテンプレートの適用

## ProjectContextのAI制御効果

AIの出力品質は入力の質に直結する。

| 状態                                        | AI出力品質                                                                 |
| ------------------------------------------- | -------------------------------------------------------------------------- |
| **未設定**                                  | 汎用的で的外れな出力（ドメイン用語を間違える、技術スタックに合わない提案） |
| **最低限**（product.yaml + technical.yaml） | 大幅に向上。プロジェクトの方向性と技術制約を理解した出力                   |
| **充実**（全ファイル + domain/\*.md）       | プロジェクト固有の正確な出力                                               |

### ユーザーが編集するファイル

| ファイル         | 内容                               | AIへの影響                 |
| ---------------- | ---------------------------------- | -------------------------- |
| `product.yaml`   | ビジョン、課題、ターゲットユーザー | 要件の妥当性判断に使われる |
| `technical.yaml` | 技術スタック、アーキテクチャ       | 仕様設計の品質に直結       |
| `structure.md`   | 命名規則、ディレクトリ構造         | Issue分解の精度に影響      |
| `domain/*.md`    | ドメイン固有の知識                 | 専門用語の正確な使用       |

> `context.yaml` はツールが自動管理するメタデータのため、通常は手動編集不要。

## Human-in-the-loop境界

### AIに任せてよいこと

- **構造化**: 自然言語 → EARS/User Story形式への変換
- **詳細化**: タイトル+概要 → 成功基準・複雑度見積もりの生成
- **一貫性チェック**: 要件間の矛盾検出、依存関係の推定
- **タスク分解**: 仕様 → GitHub Issue への変換

### 人間が判断すべきこと

- **優先度**: ビジネス判断に基づく優先順位付け
- **スコープ**: 何を含め、何を含めないかの決定
- **承認**: 要件・仕様の最終承認（PRマージ）
- **セキュリティ**: 認証・決済・個人情報に関する設計判断

### AI出力レビューポイント

AI出力を受け取ったら以下をチェック:

- **ドメイン知識の正確性**: AIが知らないビジネスルール・制約がないか
- **スコープの妥当性**: 要件の範囲が広すぎ/狭すぎないか
- **成功基準の検証可能性**: 実際にテストで確認できるか
- **依存関係の正確性**: 実装順序の前提が正しいか
- **セキュリティの考慮**: 認証・認可・個人情報に関する要件が漏れていないか

## 段階的詳細化パターン

一度にすべてを書こうとしない:

1. 簡潔なタイトル + 1行の説明で作成
2. AI enhance で EARS/User Story に変換、成功基準を生成
3. AI refine で細部を調整
4. 人間がレビューし、ドメイン知識で補正
5. SMARTバリデーションで品質確認
