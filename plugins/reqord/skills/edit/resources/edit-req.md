# edit req: Requirement品質改善

要件のSMART品質スコアを向上させるため、バリデーション結果・既存コード実装状況・ドメイン知識を基に改善案を提示し、承認後に適用する。

---

## Step 1: 対象要件の特定

**IDが指定されている場合:**

- 各IDの存在確認を行い、存在しないIDはエラー表示してスキップ

**IDが未指定の場合:**

1. `reqord req list --json` を実行して要件一覧を取得
2. 一覧をテーブル形式（ID / タイトル / ステータス / 優先度 / SMARTスコア）で表示
3. AskUserQuestionで対象要件IDを選択してもらう（複数選択可）

---

## Step 2: 情報収集

以下のコマンドを**並列で実行**して情報を収集する:

**グループA（並列実行）:**

- `reqord req show <id> --json` （対象ID分すべて）
- `reqord context show --json`
- `reqord req list --json`

**グループB（グループA完了後、並列実行）:**

- `reqord req validate <id> --json` （対象ID分すべて）

---

## Step 3+4: ドメイン知識の読み込み & 既存コード調査（並列実行）

以下を**並列で実行**する:

### ドメイン知識の読み込み

`context.yaml`の`files.domain`に列挙されているファイルをReadツールで読み込む（存在する場合のみ）。要件エンジニアリングに関連するドメインファイルを優先する。

### 既存コード調査

**Exploreエージェント**（Agentツール subagent_type=Explore）を起動し、対象要件に関連する既存コードの実装状況を調査する。

以下のテンプレートの `<変数>` を埋めてエージェントに渡すこと:

```
以下の要件に関連する既存コードの実装状況を調査してください。

対象要件:
<対象要件のID・タイトルをリスト>

調査観点:
1. 各要件の機能がすでに実装されているか（全部/一部/未着手）
2. 関連するスキーマ・型定義の現状
3. 関連するコマンド・サービス・リポジトリの実装状況
4. 現在のエラーハンドリングやバリデーションの実装パターン

コードは書かず、調査結果のみ報告してください。
```

---

## Step 5: 分析

Step 2〜4で収集した情報を基に、**要件ごとに**以下の観点で分析する。複数要件の場合、各要件の分析は**並列で実行**できる:

1. **バリデーション結果の確認**: issuesの内容とSMARTスコアの低いディメンションを特定
2. **既存コード実装状況**: 実装済み/未実装の機能を明記し、成功基準との整合性を確認
3. **曖昧表現**: 具体的な数値・条件・フォーマットに置き換えられる箇所
4. **成功基準**: 測定可能で検証可能か（3〜7件の範囲に収まるか）
5. **SMART基準**: 5つの観点で弱いディメンションを重点的に改善
6. **依存関係**: blockedBy/blocks/relatedToが実態に合っているか（実装順序と整合するか）
7. **format（ユーザーストーリー/EARS）**: 各フィールドが具体的に記述されているか
8. **見積もり整合性**: estimatedComplexityとestimatedHoursが一致しているか

---

## Step 6: 改善案の提示

### 出力フォーマット

まず**現状スコアサマリーテーブル**を表示:

```
| ID | タイトル | SMARTスコア | 基準数 | issues数 |
|---|---|---|---|---|
| req-NNNNNN | ... | 0.XX | N | N |
```

次に**要件ごとに**改善案を提示:

```
### N. req-NNNNNN: [タイトル]

**既存コード状況**: [実装済み/一部実装/未着手の概要]

**改善点**:
- **[改善カテゴリ]**: [現状] → [改善内容]（理由: ...）

### パッチJSON
{
  "title": "...",
  "successCriteria": [...],
  ...
}

### description.md 変更内容
（変更がある場合のみ。変更箇所と理由を明記）
```

**重要**: すべての改善案を提示した後、ユーザーの承認を得てから次のステップに進む。複数要件を一括で改善する場合は「以下の N 件の要件に改善を適用します。個別に確認しますか？それとも一括で適用しますか？」と選択肢を提示し、ユーザーの選択に従うこと。

---

## Step 7: 更新の適用

ユーザーの承認後、各要件に対してパッチを適用する:

1. パッチJSONをscratchpadディレクトリに一時ファイルとして書き出す
2. `reqord req update <id> --patch-file <パッチファイル> --json` で適用
3. description.mdの更新が必要な場合は、一時ファイルに書き出して `reqord req update <id> --description-file <ファイル>` で適用
4. 一時ファイルを削除

複数要件がある場合は順次適用し、各要件の適用結果を報告する。

**バージョン管理の注意**: approved状態の要件を更新した場合、内容の変更度合いに応じてバージョンインクリメントが必要か検討し、ユーザーに確認する（`reqord version req <id> --patch` または `--major`）。

---

## Step 8: 改善確認

更新後に再バリデーションを実行（複数要件の場合は**並列実行**）:

```bash
reqord req validate <id> --json
```

**改善前後の比較テーブル**を表示:

```
| ID | 改善前スコア | 改善後スコア | 変化 | issues変化 |
|---|---|---|---|---|
| req-NNNNNN | 0.XX | 0.YY | +0.ZZ | N → M |
```

改善後もissuesが残っている場合は、残存課題と対応方針を報告する。

### 次のステップ

```
品質をさらに確認する場合:
- バリデーション詳細: `/reqord:verify validate <req-id>`
- コンテキスト確認: `/reqord:brief <req-id>`
```
